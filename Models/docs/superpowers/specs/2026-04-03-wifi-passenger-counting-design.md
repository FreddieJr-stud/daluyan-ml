# WiFi Probe Request Passenger Counting - Design Spec

**Date:** 2026-04-03
**Status:** Draft
**Goal:** Proof-of-concept for automated passenger counting on M/B Dalaray using WiFi probe request sniffing on RPi5, to feed `passengers_on_board` into the existing ML inference pipeline.

---

## 1. Problem Statement

The existing `rpi5_bundle` ML models (Model 1A trip-level SOC, Model 1B real-time SOC) use `passengers_on_board` as an input feature. Currently this value comes from manual counts or the ridership spreadsheet. We need an automated, real-time method to estimate passenger count on the ferry.

**Approach:** Passively sniff WiFi probe requests from passengers' smartphones using the RPi5 and a USB WiFi adapter in monitor mode, then de-duplicate randomized MAC addresses to estimate the number of unique devices (and therefore people) on board.

## 2. Hardware

| Component | Details |
|---|---|
| **Compute** | Raspberry Pi 5, 4GB RAM, RPi OS Lite (headless, SSH) |
| **WiFi (network)** | Built-in BCM2712 chip (`wlan0`) — stays connected to network for SSH |
| **WiFi (sniffing)** | Tenda USB dongle, Realtek RTL8192FU (`wlan1`) — monitor mode confirmed |
| **Connectivity** | SSH via `wlan0` or Ethernet |

**Key constraint:** RPi5 built-in WiFi does NOT support monitor mode. The Tenda dongle does. If the Tenda proves unreliable, a recommended fallback is an Alfa AWUS036ACH or TP-Link TL-WN722N v1 (~$15).

**Tenda initialization:** The dongle boots in USB mass-storage mode and requires `usb_modeswitch` to switch to WiFi mode:
```bash
sudo usb_modeswitch -v 0bda -p a192 -M '5553424312345678000000000000061b000000020000000000000000000000'
```
After mode switch, it appears as `wlan1` with the `rtl8xxxu` kernel driver.

## 3. System Architecture

```
[Tenda wlan1 in monitor mode]
    --> tcpdump (capture 802.11 probe-req frames, stream to stdout)
    --> counter.py (parse, fingerprint, classify, cluster, count)
    --> passenger_count.json (output for rpi5_bundle inference)
```

### 3.1 Component: Sniffer (tcpdump)

`tcpdump` captures only probe request management frames on `wlan1`:

```bash
sudo tcpdump -i wlan1 -e -s 256 -l type mgt subtype probe-req
```

- `-e`: Print link-level header (includes MAC, RSSI)
- `-s 256`: Capture first 256 bytes (enough for IEs)
- `-l`: Line-buffered output for piping
- Filters at kernel level (BPF) — minimal CPU overhead

### 3.2 Component: Counter (counter.py)

The core Python script. Reads tcpdump stdout and performs:

**Thread 1 — Data Preparation:**
- Parse each probe request line: extract source MAC, RSSI, timestamp
- Classify MAC as **real** (globally unique, OUI-registered) or **randomized** (locally administered bit set — bit 1 of first octet)
- Extract features for fingerprinting:
  - Sequence number (12-bit, from 802.11 header)
  - Supported data rates (from Information Elements)
  - RSSI (signal strength in dBm)
  - Probed SSID (if any)
  - Timestamp of first/last detection

**Thread 2 — Estimation (runs every epoch):**
- **Real MACs:** Count unique addresses directly — these are reliable identifiers
- **Randomized MACs:** Cluster using lightweight DBSCAN on feature vectors:
  - Features: (rates_fingerprint, seq_number_pattern, avg_rssi)
  - Similar fingerprints + sequential sequence numbers + close RSSI = same device
  - Each cluster = 1 estimated device
- **Total estimate:** `real_unique + num_randomized_clusters`
- Apply configurable `correction_factor` (calibrated during testing)

**Epoch:** Configurable time window (default 120 seconds). Longer = more accurate but less responsive.

### 3.3 Component: Output (passenger_count.json)

Written at the end of each epoch:

```json
{
  "passenger_count": 12,
  "raw_devices_detected": 15,
  "real_mac_count": 3,
  "randomized_cluster_count": 12,
  "note": "passenger_count = (real_mac_count + randomized_cluster_count) * correction_factor",
  "correction_factor": 0.8,
  "confidence": "medium",
  "epoch_seconds": 120,
  "timestamp": "2026-04-03T10:30:00+08:00"
}
```

The `rpi5_bundle` inference code reads `passenger_count` as the `passengers_on_board` feature.

## 4. De-duplication Algorithm

### 4.1 MAC Classification

Check the locally-administered bit (second-least-significant bit of the first octet):

```python
def is_randomized(mac: str) -> bool:
    first_octet = int(mac.split(':')[0], 16)
    return bool(first_octet & 0x02)
```

- **Globally unique (real):** Assigned by manufacturer (OUI). Reliable identifier.
- **Locally administered (randomized):** Generated by device OS. Changes periodically. Must be clustered.

### 4.2 Feature Extraction

For each captured probe request frame:

| Feature | Source | Purpose |
|---|---|---|
| `source_mac` | 802.11 header | Primary identifier (real MACs) |
| `seq_number` | 802.11 header (12-bit) | Tracks same device across MAC changes |
| `rssi` | Radiotap header | Signal strength — spatial fingerprint |
| `supported_rates` | IE Tag 1 | Device capability fingerprint |
| `probed_ssid` | IE Tag 0 | Network the device is looking for |
| `timestamp` | Capture time | Temporal clustering |

### 4.3 Clustering (DBSCAN Lightweight)

For randomized MACs within an epoch:

1. Build feature vector per frame: `(rates_hash, seq_number, rssi, timestamp)`
2. Define distance metric:
   - Same `rates_hash` = 0 distance on that dimension, different = 1.0
   - `seq_number` distance = normalized gap (sequential = close)
   - `rssi` distance = abs difference / max_range
   - `timestamp` distance = seconds apart / epoch_length
3. Run DBSCAN with `eps` and `min_samples` tuned during calibration
4. Number of clusters = estimated unique randomized devices

**Fallback (if clustering is too noisy):** Use burst-based grouping — group sequential frames with the same MAC into bursts, then count unique (MAC, rates_hash) pairs within the epoch. Simpler but less accurate.

### 4.4 Correction Factor

Not every passenger carries a phone with WiFi on, and some carry multiple devices:

```
passenger_count = raw_device_count * correction_factor
```

Literature reports correction factors of **0.6 to 0.9** depending on demographics. For the M/B Dalaray (Philippine commuter ferry), we start with **0.8** and calibrate using ground truth from the ridership data.

## 6. Monitor Mode Setup

Script to initialize the Tenda dongle and enter monitor mode:

```bash
#!/bin/bash
# setup_monitor.sh

# Step 1: Mode-switch Tenda from USB storage to WiFi
sudo usb_modeswitch -v 0bda -p a192 \
  -M '5553424312345678000000000000061b000000020000000000000000000000'
sleep 3

# Step 2: Verify wlan1 exists
if ! iw dev wlan1 info > /dev/null 2>&1; then
  echo "ERROR: wlan1 not found after mode switch"
  exit 1
fi

# Step 3: Put wlan1 in monitor mode
sudo ip link set wlan1 down
sudo iw dev wlan1 set type monitor
sudo ip link set wlan1 up

# Step 4: Verify monitor mode
MODE=$(iw dev wlan1 info | grep type | awk '{print $2}')
if [ "$MODE" = "monitor" ]; then
  echo "OK: wlan1 is in monitor mode"
else
  echo "ERROR: wlan1 is in '$MODE' mode, expected 'monitor'"
  exit 1
fi
```

## 7. Testing Protocol (Home Bench Test)

**Environment:** Home, 1-10 known people with known devices.

### Phase 1: Raw Capture Validation
1. Run `setup_monitor.sh` to enter monitor mode
2. Run `sudo tcpdump -i wlan1 -e -s 256 -l type mgt subtype probe-req` for 2 minutes
3. **Success criteria:** See probe request frames in output (any at all)
4. Count how many unique MACs appear vs. how many phones are in the house

### Phase 2: Counter Script Validation
1. Run the full pipeline: `tcpdump | python3 counter.py`
2. Ground truth: note exactly which phones are present (make, model, WiFi on/off)
3. Run for 5-minute epochs, compare estimated count vs. actual
4. Test scenarios:
   - All phones WiFi ON, not connected to anything
   - All phones connected to home WiFi
   - Mix of connected and disconnected
   - Person leaves with phone, check if count decreases

### Phase 3: Calibration
1. Run multiple 5-minute epochs with known ground truth
2. Compute `correction_factor = mean(actual / detected)` across runs
3. Assess confidence: if variance is low, the factor is reliable

### Phase 4: Stress & Edge Cases
1. Test with Bluetooth-only phones (WiFi off) — expect miss
2. Test with tablets, laptops — expect detection
3. Measure CPU and RAM usage on RPi5 during capture
4. Verify `wlan0` SSH remains stable while `wlan1` sniffs

## 8. Known Limitations & Risks

| Risk | Impact | Mitigation |
|---|---|---|
| MAC randomization makes counting hard | Over/under count | DBSCAN clustering + calibration factor |
| Some passengers have WiFi off | Undercount | Correction factor accounts for this |
| Crew/staff phones counted | Overcount | Whitelist known crew MACs (subtract from count) |
| Multiple devices per person | Overcount | Correction factor; could fingerprint by rates |
| RTL8192FU is 2.4GHz only (802.11n) | Misses 5GHz-only probes | Most phones probe on 2.4GHz too; acceptable for PoC |
| Tenda dongle requires mode-switch on every boot | Fragile startup | Automated in setup script; udev rule as enhancement |
| Ferry metal hull may affect signal | Unknown range/attenuation | Test placement; RPi5 is inside the cabin with passengers |

## 9. Future Enhancements (Out of Scope for PoC)

- **Channel hopping:** Scan across 2.4GHz channels 1, 6, 11 to catch more probes
- **BLE hybrid:** Combine Bluetooth scanning for phones with WiFi off
- **Live dashboard integration:** Stream count to the Flutter dashboard
- **Automatic calibration:** Use ridership ground truth to auto-tune correction factor over time
- **udev rule:** Auto-mode-switch the Tenda dongle on USB insert
